# Рабочий цикл разработки ASHYQ

Harness — общая обвязка вокруг работы агента: контекст, границы задачи, инструменты, обратная связь и проверяемое завершение. Он действует во всём текущем репозитории `ashyq-diagnostic`: публичный сайт, обучение, профиль, API, контент и инфраструктура. Другие репозитории ASHYQ пока не подключены; для них нужно перенести политику с их собственными командами и владельцами.

## Начало задачи

1. Выполнить прежний протокол AGENTS/HANDOFF: свежий Git, проверка владельцев, опубликованный claim и отдельный worktree.
2. Добавить `harness/tasks/<ID>.json` по одному из рабочих примеров. Указать цель, точные пути, критерии готовности, контрпримеры, проверки и обязательные виды ревью. Изменять план вместе с областью задачи; не расширять его молча после выхода за scope.
3. Выполнить `node scripts/harness.mjs plan --base origin/main`, затем `check`. План показывает затронутые области, проверки и выход за границы. Только планы, изменённые в этом PR, могут покрывать его изменения. Обновление одного HANDOFF допускается отдельно.

## Выполнение и доказательства

```sh
node scripts/harness.mjs check --base origin/main
node scripts/harness.mjs run --base origin/main --checks harness,lint,types,build,units,content
# Отдельно запустить локальную production-сборку. BASE_URL должен указывать на loopback HTTP.
node scripts/harness.mjs run --base origin/main --checks seo
node scripts/harness.mjs verify --base origin/main
```

Команды выбираются по ID из `harness/policy.json`. Runner запускает Node/npm без оболочки, не принимает произвольную shell-строку, ограничивает сетевую SEO-проверку localhost и не запускается в production. Одноразовые операции подготовки облачной БД в локальном runner отключены; миграции требуют отдельной задачи и её реальных проверок.

Отчёт `.data/harness/run.json` содержит HEAD, базовый commit, отпечаток изменённых источников, коды завершения, длительность и SHA256 потоков вывода. Последовательные запуски дополняют отчёт только при совпадающих источниках. После редактирования или нового commit старый отчёт отклоняется. Завершение команды по timeout/сигналу считается провалом. Отчёты не коммитятся; полный CI остаётся отдельным авторитетным свидетельством.

CI проверяет scope/планы/риски, отрицательные примеры самого harness, структуру контентных доказательств и действительно запускает существующий `check:seo` после общего браузерного прогона. Прежние lint/types/build/bank/LMS/CRM/audio/season/tokens/a11y проверки сохранены. Impact record доступен как артефакт `harness-<run>`.

## Ревью и выпуск

Ревью проверяет хотя бы один конкретный способ сломать изменение. Для UI сохранить и просмотреть картинки на узком и широком экране; для состояния — старые записи, повтор/отмену и восстановление; для API — чужого пользователя и отказ доступа; для контента — первоисточник и границу утверждения. Карта областей: [architecture.md](architecture.md).

После точного успешного полного CI объединить проверенный commit. Повторить затронутые проверки на объединённом дереве. Проверить настоящий production URL и идентичность нужного контента/ассета, затем закрыть запись в HANDOFF. Успех сборки не подтверждает деплой, локальные фикстуры не подтверждают реальный RLS, а публикация не подтверждает индексирование или рекомендацию ИИ.

## Что можно измерить

Сохранять фактическую длительность проверок, число отклонённых выходов за scope/устаревших отчётов, повторных открытий ошибок и исправлений после выпуска. Начального сопоставимого baseline пока нет: проценты ускорения или снижения ошибок не заявляются. Полный CI по-прежнему выполняется; harness сначала сокращает выбор и повторное объяснение проверок, а не обещает меньшую длительность pipeline.

Обязательность проверки реализована в workflow и инструкции агента. Настройки branch protection GitHub не изменены. Самостоятельно написанный JSON не является криптографическим доказательством, экспертным одобрением или независимой проверкой правдивости; изменения самой политики требуют ревью как код.
