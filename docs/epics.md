`PRODUCT_BACKLOG.md` (задачи с DoD), `HANDOFF.md` §4–5 (фактическое состояние)

Связь документов: `PRODUCT_BACKLOG.md` — реестр отдельных задач (unit работы,

эпик — не claim и владение задачами не меняет. Правило обновления: при

backlog/HANDOFF; противоречия разрешать в пользу `HANDOFF.md`.

## E1 — Launch readiness (публичный продакшен-запуск)

**Goal**: вывести сайт в устойчивый публичный продакшен на собственном домене без потери заявок.

**Приоритет**: P0 — всё остальное (лиды, конверсия, аналитика) имеет смысл только на работающем production.

**Scope (stories)**:
- **E1-S1** — As a владелец, I want CI с обязательными release gates, so that ни один сломанный PR не попадает в `main`. (CI-RELEASE-001 — done; workflow `8fc121c`; branch protection пока не включена владельцем — остаточный шаг)
- **E1-S2** — As a владелец, I want корректные canonical/OG на всех маршрутах, so that поисковики индексируют правильные URL. (SEO-META-001 — done, commit `ae3bdfe`; в production обязателен реальный `NEXT_PUBLIC_SITE_URL`)
- **E1-S3** — As a оператор, I want заявки, которые не теряются при сбоях Telegram/webhook, so that ни один лид не пропадает. (LEADS-DURABILITY-001 — done: write-ahead JSONL, dedupeKey 24ч, outbox-ledger, retry, backup; постоянная БД отложена в DEPLOY-001)
- **E1-S4** — As a владелец, I want production deployment с доменом, env/secrets и health-check, so that сайт доступен пользователям 24/7. (DEPLOY-001 — READY; после security-аудита SEC-AUDIT-001 done)
- **E1-S5** — As a владелец, I want предсказуемые системные состояния (404/error/maintenance), so что сбои не выглядят как сломанный продукт. (ERROR-STATES-001 — done; offline/PWA осознанно вне scope)

**Definition of done**: сайт доступен по реальному домену с валидным HTTPS; `NEXT_PUBLIC_SITE_URL` задан и `check:seo` не содержит localhost; лиды переживают рестарт процесса и сбои каналов доставки (проверено e2e, 116/116); branch protection в GitHub включена по `docs/CI.md`; health-check и preview deployments настроены; sitemap не содержит служебных/noindex маршрутов.

**Зависимости**: DEPLOY-001 после SEO-META-001, LEADS-DURABILITY-001, SEC-AUDIT-001 (все done). Branch protection — действие владельца репозитория.

**Риски/открытые вопросы**: hosting/домен/БД не выбраны пользователем (см. «Открытые решения»); JSONL-хранилище не переживает снос диска (бэкапы смягчают, постоянная БД — в DEPLOY-001); ledger доставки растёт бесконечно (чистка не заложена).

**Статус**: In Progress (3 из ключевых задач done, DEPLOY-001 — READY и блокирует закрытие эпика).

## E2 — Conversion funnel (диагностика → лид)

**Goal**: превратить визит в заявку: довести пользователя от главной до отправленного лида с минимальными потерями на каждом шаге.

**Приоритет**: P0 — диагностика как лидген и формы заявок — ядро бизнес-модели сайта; отдельные задачи могут быть P1 по backlog, но эпик в целом критичен для запуска.

**Scope (stories)**:
- **E2-S1** — As a посетитель, I want пройти диагностику и оставить контакты без дублей и потерь, so что со мной связались. (LEADS-DURABILITY-001, CONTACT-FORM-001 — done: отдельные `kind: season`/`kind: contact`, идемпотентность, e2e 103/103)
- **E2-S2** — As a посетитель, I want отдельные страницы IELTS и SAT с программой, форматом и стоимостью, so что я могу принять решение о курсе. (COURSE-DETAILS-001 — READY; нужны подтверждённые коммерческие данные и преподаватели)
- **E2-S3** — As a посетитель, I want подписаться на новые материалы, so что получать их без заявки на сезон. (SUBSCRIBE-001 — READY; форма сейчас ведёт в заявку `/season`, бэкенда рассылки нет; нужен выбор сервиса рассылки)
- **E2-S4** — As a мобильный пользователь, I want видеть контент сразу, so что пустые зоны scroll-reveal не выглядят как сломанная страница. (находка UX-аудита №3: scroll-reveal оставляет большие пустые зоны при загрузке на мобильных `/` и `/diagnostic`; P1 UX)
- **E2-S5** — As a посетитель квиза, I want не видеть «Финиш» до конца и не терять варианты под просвечивающей панелью, so что интерфейс не сбивает с пути. (находка №5: кнопка «Финиш» видна с первого вопроса, липкая панель просвечивает над вариантами)
- **E2-S6** — As a десктоп-пользователь, I want видеть «Контакты» в шапке, so что связаться с клубом можно без прокрутки до футера. (находка №6; mobile menu и footer уже содержат ссылку — V3-CONTACTS-001/SITE-SEARCH-001)

**Definition of done**: замер воронки landing → start → completion → lead работает (E8); обе формы (season/contact) проходят e2e и видны в CRM с разными kind; страницы курсов опубликованы с подтверждёнными данными; подписка имеет double opt-in и отписку; дефекты E2-S4/E2-S5/E2-S6 исправлены и покрыты визуальными/e2e-проверками на 1440/390.

**Зависимости**: E2-S2 требует коммерческих данных от пользователя; E2-S3 — выбор рассылочного провайдера; замер воронки — E8 (ANALYTICS-001).

**Риски/открытые вопросы**: без COURSE-DETAILS-001 каталог остаётся витриной без цен и расписания (сейчас честно «по запросу»/нет данных); UX-находки 3/5 не имеют task ID в backlog — при планировании завести отдельные задачи или включить в существующие (A11Y-PERF-001/E2-S5 — квиз-файлы).

**Статус**: Ready (формы и лид-пайплайн готовы; страницы курсов, подписка и UX-фиксы — впереди).

## E3 — Operator CRM (работа оператора с лидами)

**Goal**: дать оператору надёжное рабочее место для обработки лидов — от очереди до аналитики и многопользовательской production-версии.

**Приоритет**: P1 — CRM MVP уже работает и приносит пользу; production-уровень нужен до масштабирования на нескольких менеджеров.

**Scope (stories)**:
- **E3-S1** — As a оператор, I want очередь лидов с этапами и заметками, so что я не теряю обращения. (CRM-001 — done, commit `88ce4c7`; далее SEC-AUDIT-001 — done: ключ только в заголовках, CSP, timing-safe сравнение)
- **E3-S2** — As a оператор, I want видеть статус доставки каждой заявки и повторять её, so что сбои Telegram/webhook не теряют лиды молча. (LEADS-DURABILITY-001 — done: outbox-ledger, бейдж «Не доставлено», авто/ручной retry)
- **E3-S3** — As a оператор, I want аналитику прямо в CRM (воронка по kind, лиды за 7/14 дней, топ источников по utm), so что я вижу, откуда приходят лиды. (CRM-ANALYTICS-001 — IN_PROGRESS: контракт `stats.analytics` в снапшоте, секция «Аналитика» в CrmDashboard)
- **E3-S4** — As a менеджер, I want персональную авторизацию, RBAC и назначение лидов, so что несколько человек работают в CRM без общего ключа. (CRM-PROD-001 — BLOCKED: нужны auth/БД/deployment decisions; JSONL MVP сохраняется до миграции)

**Definition of done**: CRM-ANALYTICS-001 смержена и покрыта e2e по контракту; для CRM-PROD-001 — постоянная БД, персональные аккаунты, RBAC, назначение лидов, задачи, история коммуникаций, отчёты и backup; миграция JSONL→БД без потери существующих записей.

**Зависимости**: CRM-PROD-001 зависит от решений пользователя по auth/БД (пересекается с E1/DEPLOY-001 и E6/SEASON-AUTH-001 — единый auth-стек желателен); CRM-ANALYTICS-001 не блокируется ничем.

**Риски/открытые вопросы**: общий `ASHYQ_ADMIN_KEY` без лимита попыток — известный остаточный риск SEC-AUDIT-001, закрывается CRM-PROD-001; авто-retry срабатывает только при открытии CRM; ledger растёт бесконечно.

**Статус**: In Progress (MVP и durability done, аналитика в работе, production-версия blocked).

## E4 — Trust & content (доверие и контент)

**Goal**: заменить демо-контент и бездоказательные цифры на подтверждённые материалы, чтобы сайт заслуживал доверия родителей и учеников.

**Приоритет**: P1 — продукт уже честно помечает демо-контент (плашки, noindex), но без реального контента доверие и SEO не растут.

**Scope (stories)**:
- **E4-S1** — As a родитель, I want видеть реальные отзывы, результаты и преподавателей, so что я доверяю клубу свои деньги и ребёнка. (TRUST-CONTENT-001 — BLOCKED: нужны материалы пользователя; правило — не придумывать имена, цифры и отзывы)
- **E4-S2** — As a читатель, I want настоящие статьи на `/blog/[slug]` с автором, датой и метаданными, so что блог даёт пользу и трафик. (BLOG-CONTENT-001 — BLOCKED: нужны статьи; сейчас демо-темы за флагом `BLOG_IS_DEMO`, noindex, не в sitemap — V3-BLOG-001)
- **E4-S3** — As a посетитель блога, I want у каждой статьи свой title/description в поиске и соцсетях, so что ссылки выглядят правильно при шэринге. (находка аудита №2: у `/blog/[slug]` единый статический title, нет `generateMetadata`; завести как подзадачу BLOG-CONTENT-001 или отдельный task ID)
- **E4-S4** — As a посетитель, I want цифры на главной («12 000+ / 4.8 / 90%») с источником или заменённые на проверяемые, so что сайт не противоречит собственному честному тону. (находка аудита №4; конфликтует с принципом «не придумывать цифры» из backlog)
- **E4-S5** — As a посетитель, I want реальные фотографии курсов и команды вместо повторяющихся снимков, so что сайт выглядит живым. (см. риски V3-COURSES-001/V3-ABOUT-001: в `public/brand` только 2 фото; входит в TRUST-CONTENT-001)

**Definition of done**: каждый факт доверия имеет источник; `BLOG_IS_DEMO = false`, `/blog` и `/blog/[slug]` в `SITE_ROUTES`/sitemap, у статей уникальные metadata; на главной нет неподтверждённых цифр (сноска или замена); фото не дублируются между карточками.

**Зависимости**: полностью блокированы материалами пользователя (статьи, отзывы, подтверждённые цифры, фото).

**Риски/открытые вопросы**: находки №2 и №4 не имеют task ID в backlog — при планировании включить в BLOG-CONTENT-001/TRUST-CONTENT-001 или завести отдельные; до появления контента `/blog` осознанно не индексируется.

**Статус**: Blocked (ждут материалы пользователя; технические находки №2/№4 можно делать независимо).

## E5 — Learning product (обучение: диагностика, LMS, аккаунт)

**Goal**: превратить диагностику и демо-LMS в полноценный учебный продукт с сохранением прогресса между устройствами.

**Приоритет**: P1 — учебный слой — вторая опора продукта после лидогенерации; контент диагностики влияет на качество лидов.

**Scope (stories)**:
- **E5-S1** — As a ученик, I want методически выверенную диагностику (калиброванный банк, студийное аудио, честная оценка Writing/Speaking), so что предварительная оценка реально помогает. (DIAGNOSTIC-CONTENT-001 — READY; нужны методист и студийные записи)
- **E5-S2** — As a ученик, I want классы, задания и оценки в демо-LMS, so что я вижу, как устроено обучение. (LMS-001 — done, PR #3: роли student/teacher/author, `/login`, `/me`, `/teacher`, `/write`, `/blog/[slug]`; демо в localStorage `ashyq:v2:*` за интерфейсами под Supabase)
- **E5-S3** — As a ученик, I want аккаунт с облачным прогрессом и экспортом/удалением данных, so что результаты не теряются при смене устройства. (STUDENT-ACCOUNT-001 — BLOCKED: production auth/БД и guardian policy требуют решения)
- **E5-S4** — As a владелец, I want понимать границы текущей LMS-защиты, so что демо не принимают за продакшен. (находка аудита №7: права только на клиенте, пароли демо не хешируются — задокументировано в LMS-001, закрывается Supabase-реализацией с RLS)

**Definition of done**: банк расширен и откалиброван, Listening — студийное аудио, интерпретация диапазонов подтверждена, Writing/Speaking спроектированы без обещания официального score; LMS работает на серверном auth+БД с RLS и миграцией localStorage без потери результатов; у ученика есть экспорт и удаление данных.

**Зависимости**: STUDENT-ACCOUNT-001 и серверная LMS зависят от выбора auth/БД (Supabase — заявленная точка интеграции; пересекается с E3/E6); DIAGNOSTIC-CONTENT-001 — от методиста и записей.

**Риски/открытые вопросы**: клиентская защита LMS и localStorage-данные — осознанные ограничения демо; карточка результата рассчитана на текущие 2 секции — расширение банка потребует новой компоновки PNG (V3-CARD-IMAGE-001).

**Статус**: Ready (контентная часть разблокирована; аккаунт — blocked до решений пользователя).

**Scope (stories)**:
- **E8-S1** — As a владелец, I want события диагностики в dataLayer (landing → start → completion → lead), so что я вижу воронку до подключения провайдера. (готово: `src/lib/analytics.ts` — типизированные события, `window.dataLayer`, dev-консоль; точка подключения провайдера — `track()`)
- **E8-S2** — As a владелец, I want реального провайдера аналитики с consent, so что измерение соответствует законодательству и я вижу реальные цифры. (ANALYTICS-001 — READY: нужен выбор GA4/Метрика/другой и идентификатор; зарезервированные события отправить или удалить; проверка воронки landing → start → completion → lead → enrollment)
- **E8-S3** — As a оператор, I want CRM-аналитику без внешних провайдеров, so что я вижу источники и воронку по своим данным. (CRM-ANALYTICS-001 — IN_PROGRESS: `stats.analytics` — leadsLast7Days, funnel по kind, bySource по utm_source, last14Days)
- **E8-S4** — As a пользователь сайта, I want явно дать или отозвать согласие на аналитику, so что моё согласие управляет трекингом. (consent входит в DoD ANALYTICS-001)

**Definition of done**: провайдер подключён в `track()` без изменений UI; consent реализован и уважается до отправки событий; событийная воронка проверена сквозным сценарием; CRM-аналитика смержена с e2e по контракту; зарезервированные события либо отправляются, либо удалены.

**Зависимости**: выбор провайдера и идентификатора — решение пользователя; enrollment-ступень воронки зависит от E2-S2 (курсы) и CRM-данных.

**Риски/открытые вопросы**: без consent-механики подключение провайдера делать нельзя (порядок: consent → провайдер); dataLayer-события сейчас никем не потребляются — провайдер или удалить; utm-разметка кампаний пока не определена.

**Статус**: Ready (событийная база и CRM-часть в работе; внешний провайдер — после выбора).

## Открытые решения пользователя

Эпики E1–E8 частично заблокированы решениями, которые может принять только
владелец. Пользователю обещано напомнить про вставку реальных данных.

1. **БД и деплой** (E1, E3, E5): hosting, домен, `NEXT_PUBLIC_SITE_URL`; постоянная БД для лидов — предложение LEADS-DURABILITY-001: Postgres/Supabase за интерфейсом `appendLead`/`readJsonLines`.
2. **Провайдер аналитики** (E8): GA4 / Метрика / другой — выбор + идентификатор + consent-механика.
3. **Сервис рассылки** (E2, SUBSCRIBE-001): double opt-in и отписка.
4. **Коммерческие данные** (E2, E4): цены, расписание и статус набора курсов, преподаватели, статьи, отзывы, результаты, реальные фото, подтверждённые цифры для главной.
5. **Auth и guardian policy** (E3, E5, E6): метод входа в чемпионат (OTP/e-mail/invite), правила для несовершеннолетних, scoring/appeal rules, единый auth-стек для CRM/LMS/сезона.
